# 红果取流车道

> 适用版本：1.2.0 起。报错「暂时无法播放。红果取流失败：红果 App 播放器接口对本次设备返回空响应……」对应本文的「全车道失败」分支。

## 1. 为什么会出现那个报错

红果的播放接口不会返回 4xx/5xx，它**静默返回 0 字节 200**。一旦参数或签名不被认可，调用方只会看到空体。历史上依次踩过三个坑：

| 坑 | 表现 | 现状 |
| --- | --- | --- |
| 版本四元组不自洽（`version_code` / `manifest_version_code` / `update_version_code` / `pv_player` 相互不一致） | 200 + 0 字节 | 已修：`playbackQuery` 用 `appQuery` 全字段叠加自洽的 73932 四元组 |
| 端点迁移（`/novel/player/multi_video_model/player/v1` 已死） | 200 + 0 字节 | 已修：`paths.videoModel` 指向 `/novel/player/multi_video_model/v1/` |
| V5 头组合被风控（`X-Helios` + 长 `X-Medusa` 且无 `X-Gorgon`） | 200 + 0 字节 | 已修：默认走 `gorgon` + 短 `X-Medusa`，V5 仅作兜底 |

旧代码在空体后的动作是「换设备」，而 `device_register` 按 IP 限流（连发几次就 444），设备换不出来 → 网页车道又被 30 分钟锁住 → 用户看到那句报错。**根因不在网络，在参数与签名。**

## 2. 三层兜底阶梯

```
appMedia(videoId, seriesId)
├─ ① 版本档位 × 端点车道 × 签名方案   （最便宜，覆盖绝大多数失效）
├─ ② 设备身份：辅助设备 → 主设备轮换   （只有 ① 全空才动手）
├─ ③ 网页车道 webMedia                 （受保护播放接口，失败即锁 30 分钟）
└─ 全失败 → 统一文案 + 各车道原因
```

### 2.1 第一层：档位 × 车道 × 签名

- **版本档位**（`playbackProfiles`）：一组自洽的 `{版本四元组, 机型, 渠道, UA}`。服务器只校验四元组自洽，具体版本号可换，所以换档位是有效兜底轴。默认顺序 `default(73932) > vivo-74332 > legacy-71332`，最近成功的档位会被记 30 分钟并置顶。
- **端点车道**（`playbackLaneList()`）：

  | 车道 | 地址 | 状态 |
  | --- | --- | --- |
  | `multi-main` | `api5-normal-sinfonlineb` + `/novel/player/multi_video_model/v1/` | 主力 |
  | `multi-alt` | `api5-normal-sinfonlinea` + 同上 | 可用 |
  | `player-main` | `/novel/player/multi_video_model/player/v1` | 已死，留作监测 |
  | `single-main` | `/novel/player/video_model/v1/` | 已死，留作监测 |

- **签名方案**（`playbackSigners`）：`gorgon`（`X-Gorgon` + 短 `X-Medusa`，**首选**）、`v5-stripped`（`X-Khronos` + 短 `X-Medusa`，无 `X-Helios`）、`v5`（完整 V5）。

单次 `fetchPlayerMedia` 会按「档位 → 车道 → 签名」三层循环，整套只发 1 个请求就命中时约 240 ms。命中后立刻把该车道、该签名、该档位标记为 warm。

### 2.2 健康记忆

| 缓存键 | 含义 | 时长 |
| --- | --- | --- |
| `lane-cold:<lane@platform[#profile]>` | 该车道空响应，暂时跳过 | 10 分钟 |
| `lane-ok:<key>` | 该车道刚成功，排序置顶 | 30 分钟 |
| `lane-cold-index` | 冷却车道索引，用于批量恢复 | — |
| `signer:<key>` | 该车道最近可用的签名方案 | — |
| `profile` | 最近成功的版本档位 | 30 分钟 |

冷却到期自动恢复，不需要外部触发；设备注册成功后 `laneClearCold()` 一次清空，保证「换了新身份」不会被旧的冷却记录绑住。

### 2.3 第二层：设备身份

```
ensureDevice(rejected=true)  → 辅助设备（helper），仅用于播放车道
ensureDevice(false)          → 主设备轮换（deviceRotateMs = 2 分钟限频）
```

注册先走 `registerDevice()`（`log.snssdk.com/service/2/device_register/` + 完整设备头），失败（典型是 IP 级 444）再走 `registerDeviceAlt()`（参考实现的裸头 + `magic_tag` 载荷）。两者都失败才写 `registerPause`。

### 2.4 第三层：网页车道

`webMedia()` 走 `hongguoduanju.com/api/video/protected/`。这层最容易触发「拒绝该集」，所以失败才写锁（`weblocked:<videoId>`，30 分钟）；已锁的集不再重复试探，直接以「网页车道该集刚被拒绝过，30 分钟内不再重试」并入文案。

## 3. 出一条新车道 / 新档位

新增端点车道（保持低成本）：

1. `paths` 加常量；
2. `playbackLaneList()` 追加 `{name, base, path}`（`name` 会成为健康记忆的键前缀，务必唯一）；
3. `node dev/lane-probe.cjs` 看真值表，确认新车道 `code=0 有该集=是`；
4. 若新车道需要额外请求头/参数，在 `signPlaybackHeaders` 或 `playbackQuery` 里按 `lane.name` 分支。

新增版本档位：

```js
{ name: "某个标签", userAgent: "com.phoenix.read/<vc> (...)", fields: {
    version_code: "<vc>", version_name: "<x.y.z>", manifest_version_code: "<vc>",
    update_version_code: "<vc>", pv_player: "<vc>", channel: "...",
    device_type: "...", device_brand: "...", os_api: "...", os_version: "..." } }
```

**四元组必须自洽**：`version_code` / `manifest_version_code` / `update_version_code` / `pv_player` 取同一个数，`version_name` 与 `version_code` 对应，UA 里的版本号也要一致。破坏了这一条，接口就静默返回空。

## 4. 诊断工具

```bash
node dev/lane-probe.cjs                 # 默认只测 gorgon：档位 × 车道
node dev/lane-probe.cjs --all           # 把 v5 / v5-stripped 也测一遍
node dev/lane-probe.cjs 7698309376561400856   # 指定集
```

输出包含：设备身份、档位/车道顺序、真值表（每格 `OK code=0 有该集=是` / `空响应(0 字节)`）、一次 `appMedia` 的耗时与画质。**线上又报「取流失败」时，先跑它**：

- 全部是 `空响应`：参数/签名整体失效 → 比对 `appQuery` 字段与官方最新版本号；
- 部分车道 $\to$ `空响应`：车道迁移 → 改 `paths` + `playbackLaneList`，无需动签名；
- 真值表全绿但 `appMedia` 失败：问题在模块内部（缓存/选流），不是网络。

## 5. 已知边界

- `video_tab` 接口当前恒 0 字节，仅作最后兜底，且带 `noRotate`，不会烧设备注册配额。
- `codec_type == bytevc2`（H.266）一律跳过，宁可降档也不返回播不了的流。
- `contentKey` 只支持 `app_v1`/`web_v1` 一类的 spade_a 结构；遇到新 tag 会抛「红果媒体密钥版本暂不支持」，此时该集在所有变体都不可解才会整体失败。
- CDN 直链需 `Referer: https://novel.snssdk.com/`，模块已在 `media.referer` 里带上。
